大数据架构设计和未来发展研究

我是一个汽车公司，研发体系的大数据部门架构设计师。
当前我掌握的大数据架构和基础情况如下。、

1.中国国内采用混合云架构，公有云使用华为云，私有云在公司服务器机房部署有cdp
华为云公有云介绍：
1）云上主要使用如下几个产品：
TCP接入服务（集群模式，有20多台虚拟机，主要和车端通讯，采集国标32960要求的国标数据）。
数据缓存kafka服务(有7个kafka集群，56台服务器，包含之前说的国标，还有企业自己定义的企标（几年前的车型只能发30秒频率的数据，车辆硬件限制），企标1秒（近几年的稍微低端的车型发1秒频率的数据），高精度数据（近几年的稍高端的车型最高发100毫秒频率的数据，大部分信号也是1秒的新增部分信号可发100毫秒，在车端将所有数据1分钟打包一包发给云端），国标扩展数据（部分的车辆，根据需求配置的发1秒频率的数据，是在国企标之外定义的可以灵活更新信号采集的一种数据，方便临时事件要求的数据业务，可快速下方更新采集，云端快速处理，在车端将所有数据10秒的数据打包一包发给云端），BMS数据（部分的车辆，根据需求配置的发1秒频率的数据，主要上传关于电池的数据，专用于电池安全业务），充电桩的数据（充电桩上传到云端的数据）)，这些kafka分为不同的集群，避免相互影响，采用kafka 3 的版本，数据写在本地服务器上，一般可保存20-72小时，利用率通常在50-60%，节假日用车高峰时有性能瓶颈，需要重点关注，其中国标/国标扩展数据（这也是为什么保留这个数据的原因，如果遇到特殊事件，可以在部门控制范围内进行快速的数据采集下发）归我们采集，其他种类的数据都是其他的研发事业部负责采集，通过kafka复制给我们。
日志采集服务（这是一个华为云MRS集群，在上面构建了28台服务器的hadoop集群，里面主要部署了hdfs和yarn,spark等组件，主要运行spark streaming任务。设计逻辑时每2分钟采集一次kafka数据，使用车架号后3位进行shuffle,写入到华为云OBS对象存储文件目录，按照小时级目录份文件，每一小时文件写完，私有云会启动一个拉取数据的任务将上一个小时的文件夹下所有数据拉到云下，进行长期存储，云上小时级的2分钟切片的文件在对象存储值保留7天，作为环冲，避免因为云上云下专线问问题，数据堆积，当前spark streaming方案已有性能瓶颈，在测试使用flink接收kafka数据）
实时服务（这是一个华为云MRS集群，在上面构建了76台服务器的hadoop集群，里面主要部署了hdfs和yarn,flink 30台，hbase 33台等组件），其中hbase主要用于单点查询，一部分如国标数据通过flink 采集写入到hbase,支持按照设备和时间进行快速抽取，一般用户监管业务或者数据导出业务（备注只有国标会放在hbase，监管有时效要求，其他数据类型体量都太大，没有强烈的诉求一般放到私有云hdfs，根据设备后三位，快速筛选文件导出，速度慢一些，重要的是少了很多hbase成本，也可以接受），flink 任务一般用户车辆告警检测，部署有50多个作业。

2）云下私有云使用如下几个产品：
离线计算服务（集群模式，有570台服务器，是大数据作业最主要的集群，大概部署有300多个离线作业，部署有CDP7.9.2版本，主要部署了hdfs/yarn/spark/hue/ranger/sqoop/oozie/hive/tiz等组件，大概41PB的存储空间）将从华为云拉取下来的小时文件写入此集群的hdfs 三副本模式,T+1合并分钟级的文件，保持后三位分区不变，从云上拉取数据到云下后，启动相应数据类型的解析spark程序，将车辆运行日志由raw原始样式，解析成可以计算的落入hive ods 层的表数据，此ods层的解析表，车辆运行的信号状态数据一般是用map(string,float)结构存储，因为车辆每个本版采集的信号不完全相同，把单个信号作为一列，无法及时调整结构应当车端的设计变化，另外车辆发几千个信号，hive表也无法很好的使用。hive的表原始数据一般存储近一年达到12PB以上，raw数据存储生命周期，至少十年，数据体量特别巨大，达到40PB以上。hive的分层结构是这样设计的ODS(原始成层数据)->DWD(详单数据，从ods中抽取的相对固定的列并且进行初步过滤处理过的数据，用于一种工况数据集，由于体量还是很大，很多业务还是直接从ods取数据)->DWB(工况层数据，从将ods或者dwd的数据按照工况聚合例如单车一次形势，聚合成的单条的实时数据)->DWS(聚合的数据，将dwb的表数据进行聚合生成，例如每个车型每月行驶次数，或者由业务直接从原始层生成dws的数据)->DM(指标数据，基于dwb或者dws计算出的直接用于指标输出的数据，例如用车次数最多的前5个车型)->APP(应用数据，原计划对外提供api的数据，目前不怎么使用)
Doris服务（集群模式，有15台服务器，用于快速的数据分析和报表数据引擎，从hive数据仓库中dwb层及以上同步过来的数据，或者从业务数据库同步过来的数据，遵从hive数据仓库的建设逻辑，比hive 查询分析快速，给报表提供数据）
Ozone存储服务（集群模式，有60台服务器，大概23PB的存储，其中已使用15PB,原来离线计算集群的raw数据，由于体量太大，老数据又使用频次不高，现已经确定将一年之前的raw数据每天滚动迁移到Ozone,已完成迁移15PB,限制hdfs还有25PB raw数据，预计还能迁移过来5PB, ozone采用纠删码技术，在1.5倍原始文件大小的情况下实现hdfs 3副本能力，限制CDP 也支持纠删码，由于领导对此还不太放心未使用 ）
测试集群（集群模式，有10台服务器，部署有CDP7.9.2版本，主要用于开发测试，抽样获取生产离线集群的hive表结构和部分样例数据，给开发人员使用，组件部署和离线计算服务的集群一致）
Presto服务（集群模式，有10台服务器，可以连接离线集群的hive表，查询数据）
中台服务（集群模式，有3台服务器，部署了一个定制的中台服务，主要用于集群管理，项目空间管理，作业调度管理，运维管理，建模管理，标准和指标管理，数据同步，数据查询，权限管理，分类分级，加密脱敏，基于表的api提供等功能，是一个针对开发者的工作平台）
数据平台（一个web服务，在中台服务未到位之前，部门开发的面向数据业务用户的一个对我平台，用户登录后，可以提交单车的数据导出任务，通过驱动spark读取hdfs过滤并解析导出单车数据csv格式，通过此平台可申请hive的表查看权限，并且能够自主查询自己权限内的表，底层的计算引擎就是Presto服务，此平台还支持用户提交数据分析作业，将业务诉求通过流程提交，数据开发人员接到流程需求，在中台开发作业，并将结果在流程返回）
新技术研究（10台服务器，在此服务器验证各种大数据新技术，例如Minio,spark on k8s, iceberg + polaris, dbeaver查询iceberg, dolphin调度器 , 日志监控功能等，基于这个集群的研究，我们在国外率先使用了基于云原生的大数据底座技术）

2.中国之外采用公有云架构，
海外分为欧洲（欧盟区域，服务器在巴黎）/美洲（巴西墨西哥，服务器在巴西首都）/澳大利亚/印度/东南亚（服务器在新加坡）/印度尼西亚/日本/韩国/乌兹别克斯坦/土耳其。这些站点由公司另一个研发事业部负责云资源管理和车辆数据的采集，通过kafka 复制到我们的kafka，然后我们开始消费并开展我们的数据业务。以上10个是当前已建设的站点，后续其他地区销量增多或者法规要求独立的还会再建设更多的站点，之前建设站点时，一般使用当地公有云招标模式，导致云环境多样，有谷歌云/aws/阿里云/腾讯云/华为云/裸金属服务器等，由于法规等问题，海外各个站点独立运行，不允许数据跨境。之前各个站点建设的时候采用的云服务商的大数据产品，如谷歌云的dataproc, aws的EMR ,华为云的MRS ,阿里云的lindrom, 裸金属服务器部署cdp, 腾讯云的EMR, 但是由于各个产品的版本不一致，升级不同步，很多业务在各个站点要反复调试，海外业务进展效率低，需要国内运维支持，今年开展了云原生技术的研究，尝试使用 k8S 统一版本，在k8s资源里面，部署版本统一的kafka,dolphin/spark/iceberg/polaris/dbeaver 等服务，使得数据接入，存储，入湖，查询等整个链路都能够实现。云原生大数据底座已将完成，印度尼西亚（8月的新站点），欧洲（9月切换，谷歌云dataproc到期），美洲（10月切换，谷歌云dataproc到期），印度（10月切换，谷歌云dataproc到期），当前要进行的韩国（11月切换，公司重新招标云厂商）/新加坡（12月切换，公司重新招标云厂商），海外业务由于并没有特别实时的监控业务，目前没有使用flink，部分区域有兄弟部门部署的doris，有些业务会导入数据到doris 

各地云介绍：
1）欧洲区域/美洲/印度/印度尼西亚：云原生大数据底座，车联网数据从另一个事业部kafka复制到我们的kafka，海外仅仅保持企标1秒和高精度数据的采集， 使用spark streaming采集数据2分钟写入对象存储，后三位分区，这个目录1月后滚动删除，T+1合并数据到天级目录，后三位分区，这个目录1年后滚动删除，spark解析raw数据到iceberg ods表，海外驻点人员通过 dbeaver 查询 iceberg表数据，通过dolphin 提交 spark 任务进行数据导出或者其他调度作业。
2）韩国/日本/土耳其/乌兹别克斯坦/新加坡：云厂商的数据底座，车联网数据从另一个事业部kafka复制到我们的kafka，海外仅仅保持企标1秒和高精度数据的采集， 使用spark streaming采集数据2分钟写入对象存储，后三位分区，这个目录1月后滚动删除，T+1合并数据到天级目录，后三位分区，这个目录1年后滚动删除，spark解析raw数据到hive ods表，海外驻点人员通过hue组件 查询 hive表数据，通过dolphin 提交 spark 任务进行数据导出或者其他调度作业。

2.部门的职责和现状
1）部门有多个业务：充电桩业务33个人（内含20个信息化开发和10个数据开发人员），主要服务新的充电桩数据处理和业务系统开发，工业软件业务 20人，主要负责工业软件中插件开发 ai加速，和各种软件之间连点成线的业务, 数据团队 23个人（架构10个，治理4个，开发和业务10个），主要负责国内国外数据底座建设，数据采集存储管理，数据治理，数据业务对接和数据开发，由于人力和历史原因，治理工作仅仅是制度未真正开展。部门当前有2个FDE团队驻扎在各个车型品牌项目组做ai 能力的赋能，当前部门有ai agent开发的能力，也有数据和信息化开发能力，部门有一个内部的即时通讯产品，包含通讯/会议/文件管理/ai agent(有一个专门开发ai的部门添加在我们产品上的如入口)
2）我对于一些待实现的业务的考虑：国内华为云上数据接入kafka需要升级本，将数据存储由服务器存储变为对象存储远端存储，破解成本和topic 的迁移难问题，海外kafka是一个单独的实例，也可以使用以上方案，并将kafka 也部署到k8s的基线节点中。spark streaming接受数据应该升级为flinK,打破计算性能瓶颈，海外也要在k8s上开始部署flink实时计算能力。云上云下小时级的公布应该优化为文件生成一批同步一批。hdfs存储的raw数据文件按照后三位分文件，虽然使得数据筛选1/1000，但是数据量依然大，需要开始使用parquet文件的布隆过滤功能（spark 3.0以上），这样还能快速过滤更多的数据。我们很多的数据计算业务由于是车联网工况类型的通常读取一段数据，根据上下文情况截取适合的数据片段，聚合成一个有意义的工况，再进行数据的处理，一般不能通过sql 实现，很多业务直接使用spark rdd，造成编码困难和性能差。当前流行的基于C++ native 的一些技术，在保留spark 分布式的基础上使用 c++的底层计算来加快 sql 计算。现在国内的CDP hive 架构是否升级为云原生的技术架构和国外保持一致，还是按照汽车的品牌，拆分成几个不同品牌的集群，然后分别提供服务。现在ai的直接数据识别是否能用在车联网数据业务中，例如给一台车一个时间段的切片数据，直接输出诊断结果，这种方式可以用在spark 上还是 flink上。

3）我对当前公司形势的一些思考：公司在冲击高端，事业部在要求技术创新和盈利，中心要求有可以向上展示的业绩，部门要有可以展开的大行活动，虽然现在数据团队人员不多，但如果能规划出不错的方向，也能调动更多人参与。目前事业部层面要求ai 提效，中心内部ai/信息化和我们数据部门目前在围绕数字主线，数据治理，ai 建模等方面在做一些事情，但目前推动还刚开始，在这种情况下作为数据架构设计，怎么给数据团队或者整个部门指明一个可开展的，创新的，技术研究方向（不要重复造轮子，要真的有创新性，有盈利的可能）。
